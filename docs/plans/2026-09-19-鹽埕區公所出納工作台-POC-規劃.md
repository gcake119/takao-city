- 文件狀態：業務領域更正後的規劃基線／待出納流程跟班盤點
- 整理日期：2026 年 9 月 19 日
- 主要使用者：鹽埕區公所秘書室出納承辦人
- 取代文件：`2026-09-19-鹽埕區公所採購工作台-POC-規劃.md`

## 1．業務領域更正

本工具的業務內容是承辦人描述的出納工作，不是採購案件管理。採購或其他單位送來的紙本資料，是出納流程的輸入來源之一，不是本工具的業務主體。

原採購工作台規劃因領域判讀錯誤而停止使用。本文件只納入目前已由使用者確認的出納情境；尚未取得的實際步驟、表單欄位及例外規則，不以推測補齊。

## 2．第一階段目的

第一階段要讓出納承辦人減少反覆使用 Word、Excel、筆記軟體及桌面便利貼維護同一批工作資訊，並讓工作進度、下一步及交接內容能在單一工作台查看。

紙本仍是正式流程的一部分。POC 不以消滅紙本或代替正式銀行、會計及簽核系統為目標。

## 3．目前確認的出納工作範圍

- 紙本文件以外的放行工作追蹤。
- 匯款工作追蹤。
- 代付款項工作追蹤。
- 每日接收高雄銀行往來帳資料。
- 例行與臨時出納工作的流程提示。
- 未完成事項、目前進度、下一步及注意事項的交接。
- 無特定效期但仍需處理的工作，預設每七天提醒檢視一次。
- 金額及案件數統計。
- XLSX 匯出。

上述項目的實際先後順序、完成條件、退回情況、例外及紙本欄位，仍待承辦人跟班盤點及實際檔案確認。

## 4．POC 邊界

### 4.1 納入

- 建立出納工作項目。
- 顯示今日、逾期、等待中、例行及待交接工作。
- 由承辦人自行更新目前步驟與下一步。
- 保存辦理歷程及修改前後紀錄。
- 管理有期限與無期限工作。
- 依確認後的口徑統計件數及金額。
- 匯出 XLSX。
- 以真實工作資料進行 Trial，邊用邊修。

### 4.2 第一階段不直接執行

- 不直接登入網路銀行代替承辦人操作。
- 不直接送出匯款、放行或付款指令。
- 不取代紙本簽核、正式會計系統或銀行系統。
- 不由 AI 判定款項是否合法、是否應付款或應由誰核准。
- 不在尚未確認介接方式前自動抓取銀行帳務資料。
- 不因文件引擎辨識結果而直接寫入正式工作資料。

## 5．核心資料概念初稿

下列名稱只是建模起點，須等實際工作檔案及流程確認後定稿：

- 工作項目：一筆需要追蹤的出納工作。
- 工作類型：放行、匯款、代付、高銀往來帳或其他例行工作。
- 流程範本：某類工作通常包含的步驟與提醒規則。
- 步驟執行紀錄：本期或本案實際做到哪一步。
- 金額資料：以紙本簽核或正式來源確認的實際金額。
- 來源文件：紙本或電子檔的來源與識別資訊。
- 往來帳批次：每日接收之高銀往來帳資料及其處理狀態。
- 待辦事項：下一個需要執行或追蹤的動作。
- 辦理歷程：處理時間、內容、結果與下一步。
- 交接項目：尚未完成事項、目前狀態、注意事項及接續方式。
- 變更紀錄：修改前後內容、時間及操作人。

資料庫結構不得直接沿用舊採購文件的案件、廠商接洽及交付模型。

## 6．待確認的流程問題

### 6.1 放行、匯款與代付

- 每類工作的起點及收到哪些紙本或電子資料。
- 實際處理順序與使用的系統。
- 哪些步驟只是登記，哪些步驟涉及金流操作。
- 完成、退回、暫停、取消及例外的判定方式。
- 同一筆工作是否可能拆成多次付款或多筆匯款。
- 是否存在經辦、覆核、放行等不同人員。

### 6.2 高銀往來帳

- 「接收」的實際管道：人工下載、電子郵件、網路銀行或其他方式。
- 檔案格式：XLSX、CSV、PDF、影像或其他格式。
- 每日如何判斷資料完整、重複、漏收或需要補件。
- 往來帳資料如何與工作項目或款項對應。
- 原始檔案是否需要保存及保存多久。

### 6.3 交接

- Trial 是只支援同一位承辦人整理交接資料，或需要代理人登入接手。
- 交接時哪些內容可看、可改、需確認或需簽收。
- 人員異動後，歷史操作人如何保留。
- 是否需要列印或匯出正式交接清單。

## 7．Trial 使用假設與風險

- Trial 先由一位出納承辦人在固定 Windows 電腦使用。
- 使用本機 Web App，服務只監聽 `127.0.0.1`。
- 承辦人自行點擊更新工作進度。
- Trial 期間允許直接修改，但背景保存修改前後紀錄。
- Trial 暫不建立完整備份方案，此決定不適用於正式導入。
- 若 Trial 要實際執行跨人員交接，必須先重新確認登入、權限、操作人識別、資料位置及備份假設，不能直接沿用單一使用者設計。

## 8．技術架構決定

```text
Vue 3＋TypeScript＋Vite
      ↓ Orval 產生的 API Client
OpenAPI
      ↓
NestJS 模組化單體
      ↓ Application Service／Repository
Drizzle ORM
      ↓
SQLite
```

- 前端不手寫重複的 API 型別。
- NestJS DTO 與 OpenAPI 是前後端契約來源。
- 資料庫列型別、API DTO 及前端表單型別分開。
- 跨表寫入使用資料庫交易。
- 資料庫結構使用版本化 Migration，不對 Trial 資料庫執行自動同步。
- 文件引擎只產生候選欄位；後端驗證並經承辦人確認後才能保存。

## 10．下一個規劃關卡

在建立正式資料表及畫面前，先取得並逐項盤點：

1. 承辦人目前使用的 Word、Excel、筆記及便利貼內容。
2. 放行、匯款、代付及高銀往來帳各一個真實案例。
3. 每個案例的紙本與電子檔來源。
4. 承辦人實際操作順序、使用系統、完成條件及例外。
5. 交接時下一位承辦人真正需要知道的資訊。

完成盤點後，再決定第一個可實際 Trial 的出納流程，不先假定四類工作能在第一版一次完成。
