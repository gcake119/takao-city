# 鹽埕區公所秘書室採購工作台 POC 規劃

- 文件狀態：初步規劃／Trial 前設計基線
- 整理日期：2026 年 9 月 19 日
- 主要使用者：鹽埕區公所秘書室採購承辦人
- 資料來源：
  - `docs/meeting-transcripts/2026-09-18-鹽埕區公所秘書室-訪談逐字稿.md`
  - `artifacts/鹽埕區公所秘書室_20260918/鹽埕區公所秘書室_需求文件.md`
  - 2026 年 9 月 19 日 POC 範圍收旂對話

## 1．文件定位

本文件整理第一階段「採購工作台」POC 與 Trial 規劃，作為後續畫面設計、資料模型、實作工作項目及現場驗證的基線。

本文件不是已核定的正式系統規格。現場 Word、Excel、筆記與便利貼軟體的實際欄位尚未取得；與現有檔案內容相關的欄位、統計分類及例外規則，待檔案提供後再定稿。

## 2．現場問題

承辦人目前需要在多個軟體間反覆切換：

- 使用 Word 表格手動更新工作進度。
- 使用 Excel 手動輸入紙本簽核通過後的採購金額。
- 待辦事項散落在筆記、桌面便利貼軟體及個人記憶中。
- 進度資料主要只保留最新狀態，缺少容易回查的歷程。
- 無法在同一個畫面查看多個案件的目前狀態、下一步及追蹤日期。
- 沒有特定效期、但仍需處理的案件，容易因為沒有截止日而沉底。

第一階段的最主要目的，是降低在 Word、Excel、筆記與便利貼之間的工具切換成本，而不是建置完整的採購業務系統。

## 3．產品定位

### 3.1 定位

> 一個給單一承辦人使用的小型採購工作台，集中管理紙本簽核完成後的採購金額、廠商接洽進度、待辦提醒、辦理歷程與金額統計。

### 3.2 產品性質

- 不是可拋棄的畫面展示。
- 是承辦人輸入真實案件、邊用邊修的持續探索式 Trial。
- Trial 開始後，新工作台取代原本用來維護同類資訊的 Word、Excel、筆記與桌面便利貼。
- 原有紙本簽核文件、會計系統與其他正式作業流程繼續保留。

## 4．使用者與執行環境

### 4.1 使用者

- Trial 只有一位採購承辦人使用。
- 使用固定的 Windows 電腦。
- Windows 作業系統帳號僅由承辦人本人使用。
- Trial 不另做應用程式登入、多人帳號、角色與權限。

### 4.2 執行方式

- 使用本機 Web App。
- 使用者透過 Windows 電腦的瀏覽器操作。
- 本機服務只監聽 `127.0.0.1`，不對區域網路或外部網路開放。
- Trial 電腦允許安裝及執行本機程式。
- 承辦人不需開啟終端機，由桌面或開始功能表捷徑啟動。

## 5．流程邊界

### 5.1 進入系統的起點

- 紙本請購程序已完成。
- 必要簽核已通過。
- 採購金額已確定。
- 承辦人開始進行廠商接洽與後續追蹤。

### 5.2 系統處理範圍

1. 建立採購案件。
2. 登錄採購金額。
3. 建立第一筆待辦。
4. 記錄廠商接洽、回覆及等待狀態。
5. 完成待辦並建立下一步。
6. 記錄預定交付日期與地點。
7. 廠商完成交付或到場後，將案件標記為接洽完成。

### 5.3 結束點

- 廠商已完成約定的交付或到場。
- 承辦人確認接洽追蹤工作已結束。
- 案件狀態轉為「接洽完成」。

「接洽完成」不代表已驗收、已核銷、已付款或已完成正式採購結案。

## 6．明確不納入第一階段

- 請購申請。
- 紙本或電子簽核。
- 採購方式、金額級距或法規適用判定。
- AI 自動決策、派案或廠商推薦。
- 報價合格判定與廠商評選。
- 驗收、核銷、控帳、付款與會計登錄。
- 正式採購結案。
- 掃描憑證辨識。
- 工程會表件自動更新。
- 完整附件與文件管理。
- 出納、廳舍修繕、主管會報及其他秘書室業務。
- 電子郵件、LINE、簡訊或行事曆通知。
- 廠商入口或請購單位入口。
- 跨機關、市府或既有採購系統串接。
- 正式雲端部署。
- 歷史 Word、Excel 與筆記資料的全自動匯入。

## 7．案件類型與日期語意

### 7.1 案件類型

同一套流程同時處理：

- 有明確期限的採購案件。
- 沒有特定效期、但仍需持續處理的採購案件。

### 7.2 日期欄位

| 欄位 | 用途 |
|---|---|
| 簽核通過日期 | 案件進入工作台的基準日期，並作為統計期間的預設口徑 |
| 案件期限 | 外部或業務要求的完成期限；無期限案件可留空 |
| 下一步處理日 | 承辦人預計何時執行下一個動作 |
| 下次檢視日 | 無明確期限案件何時重新檢視；預設每七天檢視一次，不等於案件期限 |
| 預定交付日 | 廠商預計交付或到場的日期 |

### 7.3 無期限案件規則

- 不判定為案件逾期。
- 建立案件時，系統預設將下次檢視日設為建立日後七天。
- 到達下次檢視日時，進入「今日待辦」。
- 承辦人完成檢視後，若案件仍在進行且沒有轉為有期限案件，系統預設將下次檢視日延後七天。
- 承辦人可依實際工作需要調整下次檢視日。
- 因資料異常而沒有下次檢視日時，顯示在「待排程案件」。
- 若正在等待廠商，仍需設定追蹤日期。

## 8．案件狀態

- 待聯絡。
- 接洽中。
- 等待廠商。
- 已安排交付。
- 接洽完成。
- 已暫停。
- 已取消。

案件狀態採「系統預選、承辦人確認」：

1. 承辦人填寫本次辦理結果。
2. 系統依結果預選下一個狀態。
3. 承辦人可在儲存前調整。
4. 儲存時一併更新案件、待辦、歷程與變更記錄。

系統預選只用來減少操作，不代表自動進行業務判斷。

## 9．核心功能

### 9.1 首頁工作總覽

首頁需要直接回答：

- 今天要做什麼？
- 哪些工作已經逾期？
- 哪些案件正在等廠商？
- 哪些無期限案件已到每週檢視日？
- 哪些無期限案件因資料異常而沒有下次檢視日？

最小區塊：

1. 已逾期。
2. 今日待辦。
3. 未來七日。
4. 等待廠商。
5. 本週需檢視的無期限案件。
6. 待排程案件。
7. 進行中案件。
8. 本月及本年度案件數與採購總金額。

### 9.2 案件清單

- 關鍵字搜尋。
- 依狀態篩選。
- 依簽核通過日期篩選。
- 依有期限／無期限篩選。
- 顯示篩選結果的案件數與採購金額合計。
- 可將目前篩選結果匯出為 XLSX。

### 9.3 案件頁面

集中顯示：

- 案件基本資料。
- 採購金額。
- 目前狀態。
- 目前下一步。
- 待辦清單。
- 廠商接洽紀錄。
- 辦理歷程。
- 變更紀錄。

### 9.4 快速更新

承辦人完成一次處理後，填寫：

- 本次做了什麼。
- 處理結果。
- 目前等待對象。
- 下一步。
- 下一步處理日或下次檢視日。
- 系統預選的案件狀態，可手動調整。

儲存時必須在同一筆資料庫交易內：

1. 完成原待辦。
2. 新增辦理歷程。
3. 建立下一筆待辦。
4. 更新案件狀態。
5. 寫入變更紀錄。

其中任一步驟失敗，整次更新不得部分寫入。

### 9.5 廠商接洽

目前不確定一個案件是否會同時或依序接洽多家廠商。為避免資料模型被鎖死，先保留一案多筆接洽記錄的能力。

Trial 介面維持簡單：

- 建立案件時不強迫輸入廠商。
- 第一次聯絡時新增廠商接洽紀錄。
- 一般情況只顯示目前主要廠商。
- 需要時可再新增其他廠商。
- 不做廠商資料庫、評分、推薦或報價比較。

## 10．採購金額與統計

### 10.1 金額口徑

- 在目前承辦作業情境中，紙本簽核的金額就是該採購案件的實際採購金額。
- 案件只使用一個「採購金額」欄位，不同時建立預估、核准與實際三個金額欄位。
- 採購金額不等於系統已確認的付款或核銷金額，因為第一階段不管理核銷與付款。

### 10.2 最小統計

- 指定期間案件數。
- 指定期間採購總金額。
- 本月案件數與金額。
- 本年度案件數與金額。
- 進行中案件數與金額。
- 接洽完成案件數與金額。
- 暫停、取消案件數與金額。
- 點擊統計結果時，可回查組成該數字的案件。

預設使用「簽核通過日期」決定統計期間。

### 10.3 必須共用的計算邏輯

下列功能必須共用同一套篩選與統計邏輯：

- 首頁統計。
- 統計頁。
- 案件清單合計。
- XLSX 匯出。

畫面案件數、畫面總金額、匯出列數、XLSX 金額合計及統計回查案件集合必須一致。

## 11．資料修改、刪除與變更記錄

### 11.1 使用者操作

- 案件基本資料可直接修改。
- 採購金額可直接修改。
- 待辦可修改、完成、重新開啟或刪除。
- 過去辦理歷程可直接修改。
- 畫面顯示修改後的最新內容。
- 承辦人不需額外建立更正紀錄。

### 11.2 背景變更記錄

每次修改至少保存：

- 資料類型。
- 資料識別碼。
- 操作類型：新增、修改、刪除、完成、重新開啟。
- 修改時間。
- 修改前內容。
- 修改後內容。
- 操作者固定記為「承辦人」。

### 11.3 軟刪除

- 使用者刪除後，資料從一般畫面消失。
- 資料庫不立即實體刪除，而是標記為已刪除。
- 變更記錄保留刪除前內容。
- Trial 不一定提供完整的垃圾桶介面。

## 12．資料模型初稿

### 12.1 採購案件

- 系統案件識別碼。
- 紙本案號（待現場檔案確認是否存在）。
- 案件名稱。
- 請購單位。
- 品項及數量摘要。
- 簽核通過日期。
- 採購金額。
- 是否有案件期限。
- 案件期限。
- 案件狀態。
- 預定交付日期。
- 交付地點。
- 備註。
- 建立時間。
- 最後更新時間。
- 軟刪除標記與時間。

### 12.2 待辦事項

- 待辦識別碼。
- 所屬案件。
- 待辦內容。
- 預定處理日期。
- 是否完成。
- 完成時間。
- 等待對象。
- 建立時間。
- 軟刪除標記與時間。

### 12.3 辦理歷程

- 歷程識別碼。
- 所屬案件。
- 處理時間。
- 辦理事項。
- 辦理結果。
- 等待對象。
- 更新前狀態。
- 更新後狀態。
- 下一步。
- 下次處理日期。
- 軟刪除標記與時間。

### 12.4 廠商接洽紀錄

- 接洽識別碼。
- 所屬案件。
- 廠商名稱。
- 聯絡日期與時間。
- 聯絡方式。
- 詢問事項。
- 回覆結果。
- 下次追蹤日期。

### 12.5 變更紀錄

- 變更紀錄識別碼。
- 目標資料類型與識別碼。
- 操作類型。
- 操作時間。
- 修改前內容。
- 修改後內容。
- 操作者。

## 13．XLSX 匯出

### 13.1 匯出入口

- 匯出案件清單目前篩選結果。
- 匯出全部案件。
- 匯出完整工作資料。

### 13.2 完整工作簿

完整匯出至少包含：

1. `採購案件`
2. `待辦事項`
3. `辦理歷程`
4. `廠商接洽`
5. `統計摘要`

### 13.3 匯出規則

- 金額使用 Excel 數字格式，不匯出為文字。
- 日期使用真正的試算表日期格式。
- 欄位名稱使用繁體中文。
- 凍結第一列，並啟用自動篩選。
- 採購金額顯示千分位。
- 無期限案件的期限欄保持空白。
- 不匯出不必要的內部技術欄位。
- 匯出前顯示資料筆數與篩選條件。
- 自由文字欄位必須以文字匯出，避免試算表公式注入。
- Trial 只做 XLSX 匯出，不做 XLSX 匯入。
- XLSX 是工作報表與資料取出方式，不視為完整資料庫備份。

## 14．技術架構

### 14.1 應用程式

```text
Windows 瀏覽器
      ↓ HTTP／127.0.0.1
Vue 3＋TypeScript＋Vite 前端
      ↓ Orval 產生的型別安全 API Client
OpenAPI 契約
      ↓
NestJS 本機 API
      ↓ Application Service／Repository
Drizzle ORM
      ↓
SQLite（`node:sqlite`）
      ↓
SheetJS 產生 XLSX
```

### 14.2 前端原則

- Vue 3＋TypeScript＋Vite。
- Pinia 只管理畫面與短期狀態，不作為永久資料來源。
- Vue Router 管理首頁、案件、統計與更新相關畫面。
- 瀏覽器不保存案件的永久副本。

### 14.3 前後端 API 契約

- NestJS 的請求與回應 DTO 是 HTTP 邊界的定義來源。
- NestJS 使用 `ValidationPipe` 執行輸入資料的執行時驗證。
- 使用 `@nestjs/swagger` 產生 OpenAPI 文件。
- 使用 Orval 根據 OpenAPI 產生 Vue 使用的 TypeScript 型別與 API Client。
- 前端不得為同一個 API 請求或回應另外手寫重複型別。
- 產生的 API Client 不手動修改；契約變更應先修改後端 DTO，再重新產生。
- 建置或測試流程必須檢查 OpenAPI 與產生的 Client 是否同步，避免契約漂移。
- 資料庫資料列型別、API DTO 與前端表單型別分開管理，不直接將 ORM 型別暴露給前端。
- 第一版不導入 GraphQL、`ts-rest` 或其他重疊的 API 契約框架。

### 14.4 後端分層

- NestJS Controller 只負責 HTTP 輸入、輸出與錯誤對應，不直接存取資料庫。
- Application Service 負責案件、待辦、統計、匯出及快速更新等業務流程。
- Repository 封裝 Drizzle 查詢，不讓資料庫查詢散落在 Controller 或畫面相關程式中。
- 跨案件、待辦、歷程與變更紀錄的操作，由 Application Service 定義交易邊界。
- 統計、案件清單合計、統計回查與 XLSX 匯出共用同一組查詢條件物件與 Repository 查詢邏輯。
- 第一版採模組化單體，不拆成微服務。

### 14.5 後端與資料庫原則

- SQLite 是 Trial 唯一資料來源。
- 使用 Drizzle ORM 定義資料表型別與資料存取查詢。
- 使用 Drizzle Kit 產生並執行版本化 SQL 遷移。
- 優先使用 Node.js 內建的 `node:sqlite`，減少 Windows 安裝及更新時的原生套件相依；若實作驗證發現必要限制，再以架構決策紀錄評估替換驅動。
- 啟用外鍵約束。
- 跨表更新使用資料庫交易。
- 保存資料庫結構版本。
- 所有資料庫結構變更都必須使用已納入版本控制的遷移。
- 開發環境可用工具產生遷移，但不得對承辦人使用中的 Trial 資料庫執行 Schema Push 或自動同步。
- 應用程式啟動時若遷移失敗，必須停止啟動，不得以部分更新的資料庫繼續執行。
- 時間與日期語意以 `Asia/Taipei` 為基準。

### 14.6 本機資料位置

程式與資料必須分離。資料位置可採：

```text
%LOCALAPPDATA%
└── TakaoProcurementTrial
    ├── data
    │   └── procurement.sqlite
    ├── logs
    └── exports
```

更新或重新安裝應用程式時，不得刪除、覆蓋或重新建立 `data` 目錄。

### 14.7 本機存取邊界

- 服務只監聽 `127.0.0.1`。
- 不監聽 `0.0.0.0`。
- 不接受其他電腦連線。
- API 限制允許的來源。
- 案件名稱、金額與辦理內容不寫入技術日誌。

### 14.8 Repository 邊界

- `gcake119/takao-city` 定位為 coordination repo，保存需求、規劃、架構決策、API 契約基線、跨前後端工作拆解與驗收紀錄。
- coordination repo 不放置可執行的前端或後端產品程式碼。
- 前端 Vue 應用程式使用 [`gcake119/takao-city-frondend`](https://github.com/gcake119/takao-city-frondend)。
- 後端 NestJS API 使用 [`gcake119/takao-city-backend`](https://github.com/gcake119/takao-city-backend)。
- 紙本文件電子檔的欄位擷取 Python 引擎使用 [`gcake119/takao-document-engine`](https://github.com/gcake119/takao-document-engine)。
- 三個可執行元件分別使用獨立 repo，避免部署、版本與相依套件互相綁定。
- OpenAPI 是前後端協作契約；由後端產生，並由前端使用 Orval 產生 Client。
- API 契約發生破壞性變更時，必須先在 coordination repo 留下決策與前後端遷移方式，再分別實作。
- 文件引擎只負責從輸入檔案擷取候選欄位，不直接寫入工作台資料庫；資料仍須經後端驗證及承辦人確認後才能保存。
- 文件引擎與後端之間的執行方式、輸入格式、輸出 Schema、錯誤處理及版本相容規則另行設計。
- 文件引擎已建立獨立 repo，但不因此自動納入目前第一階段 Trial；啟用時點需另行確認。

## 15．Trial 更新機制

### 15.1 持續試辦

Trial 採邊用邊修的方式。每次回饋區分為：

- 問題：原功能無法正確工作。
- 操作改善：功能正確，但操作不順。
- 新需求：原規劃中不存在的能力。

新需求仍受第一階段產品邊界約束，不因 Trial 邊用邊修而自動擴大為請購、驗收、核銷、付款或 AI 決策系統。

### 15.2 版本

- 每次更新必須有版本號。
- 畫面可查看目前版本。
- 更新資訊包含版本、發布日期及修改摘要。

### 15.3 更新體驗

1. 工作台啟動時與使用期間定期檢查版本。
2. 發現新版時顯示版本、修改摘要與更新提醒。
3. 系統直接下載開發者提供的更新檔。
4. 下載完成並驗證後，立即進入安裝。
5. 安裝完成後重新啟動本機服務並重新開啟工作台。

### 15.4 更新安全與失敗處理

- 更新檔來自固定 HTTPS 來源。
- 驗證版本號、SHA－256 與數位簽章。
- 禁止安裝比目前更舊的版本。
- 下載時使用暫存檔，驗證成功後才轉為可安裝狀態。
- 更新時暫停新的資料寫入，並等待正在執行的交易完成。
- 安裝檔只能修改程式目錄，不得修改資料目錄。
- 安裝失敗時恢復舊版程式並重新啟動。
- 更新通知與下載過程不上傳任何案件資料。

### 15.5 未儲存內容

若畫面有尚未儲存的內容：

- 阻止下載與安裝。
- 顯示哪些畫面存在未儲存內容。
- 提供「返回並儲存」與「放棄修改並更新」。
- Trial 不做自動草稿恢復。

### 15.6 資料庫遷移限制

Trial 不規劃備份方案，因此更新期間僅允許向後相容的遷移，例如：

- 新增資料表。
- 新增可留空或有預設值的欄位。
- 新增索引。
- 新增不破壞舊資料的狀態選項。

Trial 期間避免：

- 刪除欄位。
- 改變欄位資料型別。
- 大量重寫舊資料。
- 合併或破壞舊欄位。
- 使舊版無法讀取資料庫的破壞性變更。

## 16．備份與資料風險的 Trial 決定

Trial 期間明確不納入：

- 自動備份。
- 異地備份。
- 備份還原介面。
- 完整的災難復原方案。

本決定接受 Trial 電腦或資料庫故障時，可能需要重建 Trial 資料的風險。

仍需保持：

- 應用程式與 SQLite 資料目錄分離。
- 更新程式不得覆蓋資料。
- 紙本正式文件繼續保留。
- 正式導入前必須另行建立備份與還原方案。

## 17．最小畫面清單

1. 首頁／我的工作。
2. 採購案件清單。
3. 建立／編輯案件。
4. 案件詳細內容。
5. 快速更新視窗。
6. 採購統計。
7. XLSX 匯出確認。
8. 變更紀錄。
9. 版本與更新提醒。
10. 更新下載、驗證與安裝狀態。

## 18．Trial 驗證情境

Trial 應至少實際驗證：

1. 建立一件有期限案件。
2. 建立一件無期限案件，確認系統預設安排七天後檢視。
3. 登錄採購金額。
4. 建立第一筆待辦。
5. 從首頁找到今日工作。
6. 記錄一次廠商聯絡結果。
7. 將案件轉為等待廠商，並設定追蹤日期。
8. 完成原待辦並建立下一步。
9. 調整系統預選的案件狀態。
10. 查看完整辦理歷程。
11. 修改一筆金額並查看變更紀錄。
12. 修改一筆過去進度並查看變更紀錄。
13. 取消或暫停一件案件。
14. 查看本年度案件數與採購總金額。
15. 從統計數字回查案件。
16. 匯出篩選後案件。
17. 用 Microsoft Excel 開啟 XLSX，確認金額、日期與繁體中文正確。
18. 收到更新提醒，直接下載及安裝新版。
19. 有未儲存內容時，更新被正確阻止。
20. 完成無期限案件的每週檢視，確認系統預設延後七天。
21. 更新後原有案件仍可讀取。

## 19．Trial 成功指標

- 承辦人可從首頁找到當日工作。
- 承辦人可只看工作台說明案件現況。
- 更新一筆進度不需再到 Word、Excel、筆記或便利貼重複維護。
- 無明確期限案件預設每週提醒檢視一次，不會從工作清單消失。
- 畫面、案件清單、統計回查與 XLSX 的案件數及金額一致。
- 承辦人可以自行完成新版下載與安裝。

Trial 不設固定結束日期，採實際使用、發現問題、修正、更新後繼續使用的迭代方式。

## 20．實作前待確認

### 20.1 待現場檔案確認

- Word 進度表的實際欄位。
- Excel 採購金額表的實際欄位與統計方式。
- 筆記及桌面便利貼中常見的待辦寫法。
- 哪些欄位在不同檔案重複出現。
- 是否存在固定紙本案號。
- 一案是否可能接洽多家廠商。
- 採購金額追加、減項、取消及重新簽核的實際做法。
- 取消案件在金額統計中的正式口徑。

### 20.2 待更新發布設計確認

- 更新版本資訊與安裝檔的固定 HTTPS 位置。
- Windows 程式碼簽章方式。
- 啟動器／更新程式如何停止、置換及重新啟動 Node.js 服務。
- 舊版程式的保留與回復方式。

## 21．實作優先順序建議

1. 取得現場檔案，建立欄位對照與真實案例。
2. 定稿核心資料模型與案件狀態轉換。
3. 建立 SQLite 結構、遷移與資料存取層。
4. 完成案件建立、編輯、軟刪除與變更紀錄。
5. 完成待辦、快速更新與交易一致性。
6. 完成首頁、案件清單與無期限案件提示。
7. 完成金額統計與統計回查。
8. 完成 XLSX 匯出與 Microsoft Excel 驗證。
9. 完成 Windows 安裝、啟動、版本與本機存取邊界。
10. 完成更新提醒、下載、安裝、健康檢查與失敗回復。
11. 使用模擬案件驗收後，再交付承辦人開始真實 Trial。

## 22．決策摘要

| 主題 | 決定 |
|---|---|
| 核心目的 | 減少承辦人在 Word、Excel、筆記與便利貼間切換 |
| 產品形態 | 以採購案件為核心的小型待辦工作台 |
| 系統起點 | 紙本請購與簽核完成後 |
| 系統終點 | 廠商交付／到場，接洽追蹤完成 |
| 金額 | 紙本簽核金額即案件實際採購金額 |
| 案件類型 | 同時支援有期限與無明確期限案件 |
| 無期限案件提醒 | 預設每七天提醒檢視一次，承辦人可調整下次檢視日 |
| 使用者 | 一位承辦人、固定 Windows 電腦 |
| 技術形態 | Vue 3＋Orval＋OpenAPI＋NestJS＋Drizzle ORM＋SQLite |
| API 型別對齊 | NestJS DTO 產生 OpenAPI，再由 Orval 產生 Vue API Client；前端不重複手寫 API 型別 |
| 後端分層 | Controller＋Application Service＋Repository 的模組化單體 |
| 資料庫控制 | Drizzle Schema＋版本化 Migration＋Application Service 交易邊界 |
| Repository 分工 | `takao-city` 負責 coordination；`takao-city-frondend` 負責 Vue 前端；`takao-city-backend` 負責 NestJS 後端；`takao-document-engine` 負責 Python 文件欄位擷取 |
| 匯出 | 支援 XLSX，畫面與匯出共用統計口徑 |
| 登入 | Trial 不另做應用程式登入 |
| 備份 | Trial 不做備份與還原方案，明確接受相關風險 |
| 資料修改 | 允許直接修改，背景保留修改前後紀錄 |
| 刪除 | 採軟刪除 |
| 狀態 | 系統預選，承辦人儲存前可調整 |
| 廠商 | 尚不確定是否一案多廠商，資料模型先保留多筆接洽能力 |
| Trial 方式 | 輸入真實案件，邊用邊修 |
| 更新 | 顯示新版提醒，系統直接下載並立即安裝 |
| 未儲存內容 | 阻止更新，要求使用者儲存或放棄修改 |
